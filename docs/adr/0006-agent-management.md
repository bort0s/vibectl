# ADR-0006: Agent Management — Store, Lockfile, Ownership, and States

## Status

Proposed (2026-08-10). Design only; no implementation.

## Context

`vibe` gains a sixth noun. Alongside projects, manifests, detections, plans and
caches, it now manages **agents**: markdown files with frontmatter, distributed
by a git repository, installed into a project's `.claude/agents/`.

Three properties of the domain shape everything below.

**Agents are opaque payload.** `vibe` reads only enough of an agent file to
identify it — the `name` and `description` from its frontmatter — and never
interprets the body. Agency Agents is v0.3.0 and pre-1.0; anything deeper means
every upstream release breaks us. **Copy, do not interpret.**

**Installed agents are not rendered files.** This is the distinction most likely
to be got wrong by analogy, because both write files into a project. A rendered
`CLAUDE.md` (P4) carries an overwrite marker and is regenerated from the
manifest; its content is *derived*, and clobbering it loses nothing. An
installed agent is a user-editable artifact whose whole point is that you can
edit it. **The mechanisms must not be shared, and the render marker must never
appear in an agent file.**

**`.claude/agents/` is not ours.** It will hold hand-written agents and agents
installed by other tools. Every rule below follows from the same premise as
"never destructive": we may only touch what we put there.

## Decision

### 1. The store is a git clone

`vibe agents update` clones or pulls an upstream repository into a local store,
by default the `directories`-provided data directory (`~/.local/share/vibe/agents`,
`%APPDATA%\vibe\agents`, `~/Library/Application Support/vibe/agents`). Both the
store path and the upstream URL are configurable.

Git rather than an API, for four reasons that are all the same reason: it reuses
`git`, which the project already shells out to under the containment rules of
ADR-0005 §10; it needs no token; an update is a readable diff a user can
inspect; and it works against any host, or a local path, or a fork.

`update` is the **only** command that touches the network. Everything else works
fully offline against whatever the store already holds.

### 2. Two files, and the split is deliberate

**`.vibe/project.toml` — committed, declares intent.**

```toml
[agents]
installed = ["engineering-code-reviewer", "engineering-rust-refactoring-specialist"]
```

A sorted array of agent names. Nothing else — no hashes, no revisions, no
timestamps.

**`.vibe/agents.lock` — gitignored, records local filesystem state.**

The split is the load-bearing decision. Putting hashes in the manifest would
mean every teammate's `vibe agents add` produces a git diff, and the file that
describes the *project* becomes merge noise generated by each person's machine.
It also makes `vibe agents sync` fall out for free: clone the repo anywhere, run
one command, get the right agents.

Adding `[agents]` is **additive**, so it is a **minor** schema bump to `1.1` per
ADR-0002 §2. Existing manifests parse unchanged; an older binary reads a
manifest containing it, ignores the table, preserves it on write, and warns once.
That is the forward-compatibility path working as designed, and it is why the
table goes in the manifest rather than a third file.

### 3. Lockfile schema

```toml
# .vibe/agents.lock
# Generated by vibe. Local state - add to .gitignore.
lock_version = "1.0"

[[agent]]
name = "engineering-code-reviewer"
path = ".claude/agents/engineering-code-reviewer.md"
content_hash = "b3:1f9a...c4"
source_rev = "9c1d4e2f8a7b3c5d6e0f1a2b3c4d5e6f7a8b9c0d"
source_path = "engineering/code-reviewer.md"
installed_at = "2026-08-10T09:14:22Z"
```

| Field | Purpose |
| --- | --- |
| `lock_version` | `major.minor`, same discipline and same reasons as the manifest (§3a). |
| `name` | The identity `add`/`remove`/`status` use. |
| `path` | Project-relative install location. Recorded rather than derived, so a future layout change does not orphan existing installs. |
| `content_hash` | What we wrote. The **only** way to tell "unmodified" from "the user edited it". |
| `source_rev` | The store commit the content came from. Makes "outdated" answerable without the network. |
| `source_path` | Where it lived in the store. Detects an upstream *rename* as distinct from a deletion. |
| `installed_at` | RFC 3339 UTC. Diagnostic only; never compared for staleness. |

`[[agent]]` entries are sorted by `name`, so the file is stable across runs.

**`content_hash` is prefixed with its algorithm** (`b3:` for BLAKE3). A bare hex
string is a format that cannot be migrated: the day the algorithm changes, every
existing lockfile becomes a set of hashes of unknown provenance that compare
unequal, and every installed agent reports as modified. The prefix makes an
unrecognised algorithm a *known unknown* — treated as "cannot verify" rather
than "differs", which is the `NotAttempted`-versus-`Conflict` distinction
applied to hashing.

#### 3a. The lockfile gets its own version gate

A second on-disk format needs the same major/minor discipline as the manifest,
for the same reason: it will be read by builds that did not write it.

- **Major mismatch** — refuse to *write*, and treat every agent as
  unverifiable rather than as modified or missing. A build that cannot read the
  lockfile knows nothing about ownership, and §5's rule is that we never touch
  what we do not own. Refusing the write is what keeps that true.
- **Minor newer** — proceed, ignore unknown fields, preserve them on write,
  warn once.
- **Absent** — not an error. It means nothing has been installed *by us*, which
  is exactly what a fresh clone looks like. Every agent file present is
  therefore unowned (§5).

The asymmetry with the *cache* (ADR-0004 §7) is deliberate and worth stating,
because the lockfile superficially resembles one. A corrupt cache is discarded,
because it is regenerable from disk. **A corrupt lockfile is not discarded**,
because it is not regenerable: the hash of what we wrote cannot be recovered by
looking at a file the user may since have edited. Discarding it would silently
convert every installed agent into an unowned one, which is a permanent loss of
the only ownership record. A corrupt lockfile is therefore reported, and
ownership-dependent operations refuse until the user resolves it.

### 4. `add` write ordering, and crash recovery

Two files must change: the agent file, and the lockfile. Something must land
first, and the answer follows from asking which orphan is recoverable.

**The agent file lands first. The lockfile is updated second.**

Both writes are temp-plus-rename, which makes each individually atomic — but
atomicity per file is not the question. The question is what a crash *between*
them leaves, and there is no ordering that leaves nothing:

| Crash point | State on disk | Recoverable? |
| --- | --- | --- |
| After agent file, before lockfile | Agent file exists, no lock entry | **Yes.** Reports as `PresentUnowned` (§5). `add` again writes an identical file, hashes it, records it. |
| After lockfile, before agent file | Lock entry exists, no file | **No, silently.** Reports as `Missing`. But we have recorded a `content_hash` for a file we never wrote — so if the user later creates a file at that path by hand, it compares unequal and reports as `Modified`. We would be claiming ownership of, and offering to overwrite, a file we never created. |

The second is worse in kind, not degree: the first loses *a record*, the second
manufactures a *false claim of ownership*. So the file goes first, and the
lockfile — the ownership assertion — is only ever written about a file we have
confirmed on disk.

The recovery path is therefore: **an agent file with no lock entry is unowned,
and `add` is idempotent.** Running `vibe agents add <name>` again after a crash
writes the same bytes, hashes them, and records the entry. Because the content
is identical, this is safe even in the case where the crash happened after a
*successful* file write — there is no state where re-running `add` destroys
something.

`remove` inverts the order for the same reason: **lockfile entry first, then the
file.** A crash leaves a file with no entry — unowned, untouched, reported — and
never an entry pointing at a file that is gone.

**The window is contained, not closed — and the distinction matters.**

Temp-plus-rename gives atomicity **per file**. It does nothing whatever about
the gap between two atomic writes; if it did, the ordering argument above would
have been unnecessary. Calling the window "atomic" would invite a later reader
to assume it is closed and skip the state-table check on a new code path, which
is exactly the assumption that turns a named state into an unhandled one.

What makes the window acceptable is **containment**: every state it can produce
is named in §5, and every one of them recovers by running a command the user was
already running. That is the claim, and it has to be re-established for any new
code path that writes both files — it does not follow from the writes being
individually atomic.

A journal would buy exactness where the fallback is "run `add` again", at the
cost of a third on-disk format with its own versioning and its own corruption
story. Not taken.

#### 4a. Crash mid-`update`, across N agents

`update` rewrites many agents. A crash partway leaves some at the new revision,
some at the old, and the lockfile advanced for only some of them.

**This is covered, and the reason is that `source_rev` is per-agent.** Each
`[[agent]]` entry records the store commit *its own* content came from, so a
half-finished update is not a corrupt state — it is N independent per-agent
states, each of which is already in the table:

- Agents rewritten before the crash: lock entry updated, file matches →
  `Installed`, at the new revision.
- Agents not yet reached: lock entry untouched, file matches its recorded hash →
  `Installed`, at the old revision, and `status` reports them as outdated
  because their `source_rev` differs from the store `HEAD`.
- The agent being written at the moment of the crash: file written, entry not
  yet updated (per §4's ordering) → its recorded hash no longer matches the file
  → `Modified`.

The first two need no action; re-running `update` completes them. Only the third
needs the user, and it needs it for a good reason: from the lockfile alone,
"we crashed halfway through writing this" and "the user edited it" are the same
observation. Reporting it as `Modified` and refusing to overwrite without
`--force` is the honest reading, and it errs toward not destroying an edit.

**Had `source_rev` been a single store-wide field**, this would not work: a
partially-advanced global revision would describe every agent inaccurately, and
there would be no way to tell which ones had actually been rewritten. That is
the reason the field is per-`[[agent]]` rather than in the file header, and it
is worth stating because a store-wide field looks like the obvious
normalisation.

`update` writes agents in `name` order, so a crash leaves a prefix rather than
an arbitrary subset — which makes a partial state easier for a human to reason
about, though nothing depends on it.

### 5. The `status` state table

Ownership is the axis everything hangs on: **`vibe` never modifies or deletes a
file it did not install.** The lockfile is the record of what it installed.

| State | Detected by | Reported as | `add` | `remove` | `update`/`sync` |
| --- | --- | --- | --- | --- | --- |
| **Installed** | Lock entry, file exists, hash matches | `ok` | no-op | removes file + entry | overwrites if store differs |
| **Modified** | Lock entry, file exists, hash differs | `modified` | refuses without `--force` | removes (it is ours) — but warns the edit is lost | **refuses**; reports; requires `--force` |
| **Missing** | Lock entry, no file | `missing` | reinstalls | drops the entry | reinstalls |
| **PresentUnowned** | No lock entry, file exists, name matches a store agent | `unowned` | **refuses**; will not adopt | **refuses**; not ours to delete | ignores entirely |
| **Foreign** | No lock entry, file exists, no store agent of that name | not listed | n/a | n/a | ignored |
| **Orphaned** | Lock entry, file exists, name absent from store | `orphaned` | n/a | removes (still ours) | **leaves the file untouched**; reports |
| **Renamed** | Lock entry, `source_path` absent, another store agent has the same content | `orphaned (renamed upstream to X)` | n/a | as Orphaned | leaves untouched; reports the new name |
| **Declared, not installed** | In `[agents] installed`, no lock entry, no file | `declared` | installs it | n/a | installs it — this is what `sync` is *for* |
| **Installed, not declared** | Lock entry, absent from `[agents] installed` | `undeclared` | n/a | removes | **leaves it**; suggests `add` to declare it |
| **Unverifiable** | Lock entry, unrecognised hash algorithm or unreadable lockfile | `unverifiable` | refuses | refuses | refuses |

Four of these deserve their reasoning stated.

**PresentUnowned is its own state, not "modified".** A file at
`.claude/agents/engineering-code-reviewer.md` that we did not install is not a
modified copy of ours — it might be hand-written, or installed by another tool,
and calling it modified implies a relationship that does not exist. It is
reported as a distinct state precisely so the user can decide, and `add` refuses
rather than adopting: silently taking ownership of a file we did not write is
how the next `update` overwrites someone's work.

**Modified refuses rather than overwriting.** Editing an installed agent is the
*normal* reason to have installed one. This is the single most likely way for
this feature to destroy user work, and it gets the same treatment as `sync`
never overwriting a populated field.

**Orphaned never propagates a deletion.** If an agent disappears upstream, the
local file stays. Destructive is destructive regardless of who initiated it,
and "upstream deleted it" is not a user's instruction to delete their local copy.

**Undeclared is left alone, not removed.** A lock entry without a manifest
declaration usually means someone added an agent and did not commit the
manifest — the fix is to declare it, not to delete their file.

### 6. `agents sync` when the store lacks a declared agent

The manifest declares `foo`; the store does not have it. Three causes are
proposed: a stale store, an upstream deletion, or a typo.

**They are not fully distinguishable, and the design says so rather than
guessing.** What we can and cannot know:

- We **can** distinguish "was never in this store" from "was here and is gone",
  because a lock entry with a `source_rev` proves we once had it. That
  separates *orphaned* (installed, then vanished upstream) from *never seen*.
- We **cannot** distinguish a stale store from an upstream deletion without the
  network, and `sync` does not touch the network (§1).
- We **cannot** distinguish a typo from a genuinely-missing agent at all. Both
  are "a name the store does not have". Levenshtein-suggesting a near match
  would be a guess dressed as help — and this project's rule is that a plausible
  wrong answer is worse than an honest empty one.

So `sync` reports **one state — `NotInStore`** — and qualifies it with the two
facts it actually has:

```
2 declared agent(s) are not in the store:
  security-appsec-engineer
  engineering-code-reviwer

The store was last updated 12 days ago; run 'vibe agents update' first.
```

The store-age line is the crucial part, and it inherits the
`NotAttempted`-versus-`Conflict` distinction directly. **The store being stale
is a fact about this machine.** Reporting "this agent does not exist" when the
truth is "this machine has not fetched for twelve days" would be a claim about
the project — the same error as reporting `no_evidence` when `git` was missing,
or `Unreadable` on a file that never existed.

Therefore:

- `sync` **installs what it can and reports what it cannot**. A missing agent
  never fails the whole command; the other agents still install. Exit code `2`
  (partial), per ADR-0002 §3.
- The store-age line appears whenever anything is `NotInStore` **and** the store
  is older than the threshold, regardless of the usual `--json`/quiet rules.
- If the store has *never* been updated, that is said explicitly rather than
  reported as an age.
- `sync` **never removes** a manifest-declared agent from the manifest, and
  never edits the manifest at all. Declaring is the user's act.

### 7. Freshness reporting without a daemon or a hot-path network call

There is no resident process, so a "daily check" could only mean a network call
inside an unrelated command. That would destroy the P2 latency budget — one
network round-trip dwarfs the entire 654 ms scan — and break offline use.

Instead: after any command that already read the store, if the store's last
update is older than N days (configurable, default 7), emit **one stderr line**:

```
store last updated 12 days ago - run 'vibe agents update'
```

Read from the store's own git metadata, which is already on disk. Every read
command works fully offline. No command initiates network I/O except `update`.

### 8. What is explicitly out of scope

- **Agent testing.** Dropped, not deferred.
- **Interpreting agent bodies.** We read frontmatter `name` and `description`
  and nothing else.
- **Publishing or authoring agents.** `vibe` installs; it does not create.
- **Multiple stores.** One upstream, configurable. A second one is a v2
  conversation and would need precedence rules this design does not have.

## Consequences

**Easier:** `vibe agents sync` after a fresh clone gets a project's agents right
in one command, with no token and no network beyond the store. Ownership being
explicit means the feature can coexist with hand-written agents and with other
tools writing to the same directory — which is the realistic situation, not an
edge case.

**Harder:** two on-disk formats now need version discipline instead of one. The
state table is ten states, and every command has to have an answer for each; a
new state is a change to five columns. Ownership tracking means a crash window
that is reasoned about rather than eliminated.

**Trade-off accepted #1:** *the two-file write window is real and is not closed
by a journal.* Every state it can produce is named in §5 and recovered by
re-running the command the user was already running. Buying exactness here
would cost a journal format, its own versioning, and its own corruption story —
for a case whose fallback is one idempotent command.

**Trade-off accepted #2:** *a typo and a genuinely absent agent are reported
identically.* We could suggest near-matches. We will not, because the tool's
differentiating claim is that it does not offer plausible guesses, and a
suggested agent name is exactly that. The store-age line is the honest help.

**Trade-off accepted #3:** *`Modified` blocks `update` until the user acts.* A
user who edits an installed agent and then wants upstream changes must resolve
it by hand — there is no merge. Agents are opaque payload (§Context); merging
them would mean interpreting them.

**Trade-off accepted #4:** *store staleness is reported, never acted on.* A user
who ignores the line runs against a store from last year and gets
`NotInStore` for agents that exist upstream. We accept that over a network call
on the hot path, and mitigate it by naming the age rather than merely saying an
agent is missing.
